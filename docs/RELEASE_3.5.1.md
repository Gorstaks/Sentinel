# Sentinel 3.5.1: policy rollback and Defender release gate

The owner requested undoing the last three policy pushes and made antivirus acceptance, especially Microsoft Defender, the highest release priority. Functional changes in 2909dc3, 376aff9 and 732b714 were confined to GSecurity.inf; their other changes were version stamps. Restore its pre-change audit/registry settings from 2f95275 (3.4.7), without rewriting history or downgrading the package version. The subsequent owner-uploaded candidate c35cd2c was also reviewed before publication. The TLS UTC-validity fix remains intact.

This removes the new audit-disable settings and restores the previous declared UAC/registry policy. Do not restore the old global privilege-rights section: both old and uploaded policies contain broad Console Logon (S-1-2-1) grants, while recent versions empty important rights such as SeAssignPrimaryTokenPrivilege. The new candidate retains standard service impersonation privileges, so it does not establish protection against all Potato-style impersonation exploits. The shipped template now omits global user-right/logon-right replacements entirely, preserving OS/administrator assignments on future applications. This is NOT a reset to Windows defaults, a repair of already-modified rights, or a complete least-privilege certification. Previously applied empty rights do not automatically revert merely because their INF entries were removed. Other hardening and terminal detection/response stay armed.

## Defender acceptance

A reported Defender detection, PWS:MSIL/Stealer.DHC!MTB, affected Sentinel.Core.dll. Do not assume this is a false positive. The initial credential-path audit found browser-store metadata/read telemetry and DPAPI use for Sentinel's own protected state, backups, quarantine and provider key; the canary monitor reads its own planted Credential Manager targets. That limited source inspection is not a malware-clean certification or an explanation of Defender's classifier.

Local release.ps1 publication is also gated by the real scan before committing/publishing; PrepareOnly metadata preparation does not claim scan acceptance.

Build acceptance now requires an actual current-signature Defender custom scan of Core, and release publication additionally requires a scan of the exact installer and published runtime directories. Payloads are copied outside the workspace to a unique drive-root staging directory. The custom scan uses DisableRemediation to report detections rather than interpreting successful automatic remediation as a clean build; this does not disable Defender or real-time protection. Active Normal-mode Defender, real-time protection, signatures no older than 48 hours, and a validated Defender cloud connection are required. Protection can be enabled on a disposable hosted CI runner, never disabled; exclusions are not added. Engine/signature versions, stdout/stderr and SHA256 manifests are uploaded. Nonzero scanner exit, quarantined/changed payloads, stale signatures or unavailable protection block acceptance. A Linux build, passive Defender, or skipped scan never counts as passing.

A passing scan is evidence for those exact bytes, engine, signatures and environment. It cannot guarantee acceptance by all vendors, every Defender cloud classifier or future signatures. Real publisher signing can establish identity but does not guarantee antivirus acceptance; a self-signed development certificate does not establish public publisher trust. No import/string obfuscation, detection-engine removal, Defender exclusion or antivirus tampering is used to evade a verdict. If the current Defender verdict persists, publication must remain blocked pending investigation and, where appropriate, an owner-submitted Microsoft false-positive review: https://www.microsoft.com/en-us/wdsi/filesubmission . No automatic false-positive portal submissions or user credentials are supplied. Defender cloud protection may submit build samples according to its settings; the scan inputs are build artifacts, not the owner's browser data or uploaded incident logs.

## Supplied 3.5.0 incident and recovery limits

The supplied logs identify 3.5.0, successful service startup, a later detection backlog and file-lane ETW drops. SystemSettings.exe was observed with LogOnly; no supplied response proves Sentinel terminated it. The exact firewall rollback exception and cause of the black window are absent. RunUninstallCleanup currently catches exceptions and returns a generic error, and a quarantined Core dependency can prevent the cleanup executable from loading at all. Do not infer that all symptoms share one proven cause.

The response log does show an attempted OneDrive FileSyncShell64.dll quarantine: Explorer termination was refused, while file containment was deferred. A deferred action can include deletion on reboot. Preserve the Sentinel quarantine, its metadata, firewall rollback journal and Windows pending-file operations for inspection. Do not blindly clear quarantine, remove pending operations, reset the firewall, or reboot as an assumed repair.

Repository rollback and a new installer do not by themselves reverse every security setting already applied to a damaged installation. Existing firewall state is journaled separately under ProgramData/Sentinel/FirewallPolicy; do not delete that recovery state. Defender's Protection History and the full rollback error are needed for machine-specific recovery. This patch does not claim the black Settings window or the OneDrive false containment is repaired.

A read-only `tools/diagnostics/Collect-InstallFailure.ps1` (also installed under Tools) collects Defender names/history, service state, relevant application failures, firewall-journal presence and relevant pending file operations without loading Core. Run it from elevated native Windows PowerShell when collecting recovery evidence; it does not restore/remove files, change policy or reboot. It prints the local JSON path. Review before sharing because local paths and Windows error messages are included.

## New policy review

The c35cd2c candidate restores event-audit entries but grants SeDebugPrivilege, SeLoadDriverPrivilege, SeRestorePrivilege and other powerful rights to Console Logon. It also retains an empty SeAssignPrimaryTokenPrivilege assignment and duplicates SeNetworkLogonRight (a later empty assignment follows a populated one). Neither this candidate nor the older console-wide privilege grants are deployed in 3.5.1. Potato-family mitigations require patched Windows and least privilege for the actual service/account; stripping shared Windows service privileges globally is not a compatibility-safe substitute. This review does not claim exploit-specific prevention from policy text alone.
