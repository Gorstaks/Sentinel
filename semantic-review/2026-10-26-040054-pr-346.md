# Foreign-path DLL kill demoted to review-only, plus reputation-feed and containment-receipt repairs (release 3.4.6)

Release 3.4.6 (`d10d1bb..54dbaff`) makes one change that reduces response authority and several that repair or harden it. The response reduction: a mapped module whose `ModuleIdentity` verdict is the terminal `foreign-path` bucket (not in a trusted tree, but also not in a user-writable drop and not a sideload-target name) no longer triggers a host process-tree kill. It now emits a Tier2 `LogOnly` "review" event. The stated trigger is a real false positive — a `taskhostw` kill caused by RTSSHooks64.dll, a legitimate RivaTuner overlay hook. The remaining changes restore the MalwareBazaar reputation feed (the old plaintext endpoint was retired upstream and now returns HTTP 410) behind an authenticated, DPAPI-protected credential, fix the process-tree terminator to stop declaring full-tree containment when a descendant could not be opened, and coalesce ETW registry hints before the dispatch queue.

Watch for: the foreign-path demotion tags its review event `WeakObserveSeed=true`, which does more than remove the solo kill — it excludes the signal from behavioral correlation entirely (confirmed). That is the one place where the change removes genuine coverage rather than just downgrading a noisy solo action, and it is the opposite of how the adjacent late-load signal was deliberately built. Everything else in the release is defensible hardening or capability restoration.

**Verdict**: NEEDS_CHANGES

## High-level view

The foreign-path demotion is defensible at the solo-kill level and is correctly scoped: the regression test proves that a user-writable-drop module and a sideload-name plant (`version.dll` in Temp) are still *not* review-only, so the two attacker-plant classes retain their kill/quarantine authority. Killing a host purely because a signed-or-unsigned DLL loaded from an unusual-but-not-writable location was closer to identity-based response than behavioral response, and the constraints forbid identity-only kills. So demoting the *solo* action is consistent with the behavioral-only-kill rule.

The problem is the correlation exclusion. The demoted event carries `WeakObserveSeed=true`, and `ResponsePolicy.IsNonCorrelatingObserveNoise` treats that flag as a signal to drop before buffering in both the weighted and behavioral correlation engines. So a foreign-path module that later does something harmful on the same PID (mass encryption, LSASS access, injection) can no longer contribute its provenance weight to a composite. The adjacent "Unexpected Late Module Load" signal was explicitly built to avoid exactly this — its own comment says it deliberately does *not* set `WeakObserveSeed` so it can still correlate. The foreign-path review path should follow that same pattern: keep it out of solo kills, keep it in the correlation buffer.

The MalwareBazaar change restores a dead capability rather than weakening a live one. The reputation path fails closed: no key, malformed key, HTTP 410, or schema-invalid response all resolve to `HashVerdict.Unknown`, never a clean or malware verdict. The credential is DPAPI-sealed under a SYSTEM/Administrators-only registry key with ACL enforcement that rejects any non-privileged allow ACE. A hash match never authorizes a process kill, only the separately-audited pinned-file policy.

The process-tree terminator change tightens fail-closed behavior. Previously an un-openable descendant was skipped and the operation still reported `DiscoveryComplete=true` and `Success=true` — a verified full-tree containment that had a hole in it. Now the refused child is recorded, `DiscoveryComplete` is false, and the receipt reports partial containment while still killing the root and every openable child. This removes a fail-open overclaim.

The certificate response path was not touched in this release. The test file gained assertions documenting the existing `CertificateNotExplicitlyDistrusted` demotion, but the engine source is unchanged in this range, so it is out of scope.

### Foreign-path kill demoted to Tier2 review

Before this release, `NotifyMappedModuleAsync` handled a non-allowed `ModuleIdentity` verdict by falling through to `ScanProcessAsync(..., forceRemediate: true)`, and the batch scanner added the module to `hostileLoaded`. Either way, a non-allowed module set `provenLoad = true` and reached `result.Containment = HardeningModule.SafeKillProcessTree(processId, ...)` plus on-disk quarantine. A `foreign-path` verdict — the terminal `return Deny("foreign-path")` that catches anything not already classified as a writable drop, sideload plant, or servicing impersonation — therefore produced a full host kill.

The release inserts `IsReviewOnlyIdentity(verdict)` ahead of both kill sites:

```csharp
internal static bool IsReviewOnlyIdentity(ModuleIdentity.Verdict verdict) =>
    !verdict.Allowed && verdict.Reason == "foreign-path";
```

When it matches, the code emits a Tier2 `LogOnly` event and `continue`s / returns, so `foreign-path` modules never enter `hostileLoaded` and never reach `SafeKillProcessTree`. The scoping is tight and verified by `Release346RegressionTests.UnknownExternalPluginIsReviewOnlyWithoutBecomingTrustedAndPlantsStayActionable`: a module in `AppData\Local\Temp` (`user-writable-drop`) and a `version.dll` in `C:\Windows\Temp` (`sideload-name-in-writable`) both return `IsReviewOnlyIdentity == false`, so they keep their containment authority. Only the pure foreign-path bucket is demoted.

Judged against the behavioral-only-kill constraint, demoting the *solo action* is defensible. A `foreign-path` module is one that sits outside every trusted tree but is not in a writable drop and does not wear a hijack name — for example a third-party overlay DLL installed under `D:\InstalledTools`. Killing the host for that alone keys on where the file lives (identity), not on an injection act the process performed (behavior). The RTSSHooks64.dll / taskhostw false positive that motivated the change is the textbook case.

The concern is the tags on the review event:

```csharp
Metadata = new Dictionary<string, string> {
    ["WeakObserveSeed"] = "true", ["ObserveOnly"] = "true", ... }
```

`ResponsePolicy.IsPureUxObserveNoise` returns true on `WeakObserveSeed=true`, and `IsNonCorrelatingObserveNoise` folds that in. Both `WeightedCorrelationEngine.Ingest` and `BehavioralCorrelationEngine.Ingest` bail when `IsNonCorrelatingObserveNoise` is true, so this signal is dropped before it enters any correlation buffer. The foreign-path module therefore contributes nothing to a composite even if the same PID subsequently encrypts files or reads LSASS.

The code one method over — `MaybeEmitUnexpectedLateLoadAsync` — documents the correct pattern and the exact trap being fallen into here:

> Deliberately NOT tagged WeakObserveSeed=true: that flag routes through IsPureUxObserveNoise -> IsNonCorrelatingObserveNoise, which RegisterSignalAsync uses to DROP a signal before buffering - it would prevent this signal from ever correlating.

The late-load signal uses a `Provenance` tag instead so it stays correlatable while still being unable to act alone (Tier2 + LogOnly + not in any terminal rule list). The foreign-path review event should do the same. As written, demoting the solo kill was the right call but the correlation exclusion silently widens it into a real coverage loss for injected-but-not-writable-drop modules.

### MalwareBazaar feed restoration and credential handling

The old feed constant `https://bazaar.abuse.ch/export/txt/sha256/recent/` was retired upstream; the regression handler returns HTTP 410 for it and asserts the new code never requests an `/export/` path. The release switches to the authenticated API (`https://mb-api.abuse.ch/api/v1/`, POST with `get_recent`/`selector=100` and an `Auth-Key` header), parses the JSON with `System.Text.Json`, and requires `query_status == "ok"`, an array `data` of at most 100 rows, and a valid SHA256 in every row — any deviation returns null and the feed state becomes "Unavailable or invalid; verdict unknown".

The fail-closed properties are verified: `MissingCredentialsAndGoneResponsesCannotCreateMalwareOrSafeVerdicts` drives null, a CRLF-injection key (`"bad\r\nkey"`), and a valid key, and asserts `HashVerdict.Unknown` in every case with a feed request issued only for the valid key. The constructor rejects keys over 256 chars or containing anything outside printable ASCII, which closes header-injection and keeps the key off any other host. The sample cap dropped from 100,000 to 100, but since the old endpoint is dead this restores a smaller live capability rather than shrinking a working one; a hash match still only feeds the audited pinned-file policy and never a process kill.

`MalwareBazaarCredential` reads a DPAPI `LocalMachine`-scoped blob from `HKLM\SOFTWARE\Sentinel\Credentials`, and before decrypting it verifies the key owner is SYSTEM or Administrators, that access rules are protected (no inheritance), and that no allow ACE grants a non-privileged SID — throwing otherwise. Any failure path logs and returns null, leaving reputation unknown. This is a non-attacker-controllable anchor for the credential, consistent with the fail-closed posture.

### Process-tree containment receipt

The terminator previously skipped a descendant that `OpenProcess` refused (ERROR_ACCESS_DENIED from a PID-reuse or racing-exit slot) and still set `DiscoveryComplete = true`, so `Success` (which is `RootExited && DiscoveryComplete && no failures && no refusals`) could report a fully verified containment over a tree it had not fully enumerated. The change records the refused PID, skips it in subsequent discovery passes, and gates `DiscoveryComplete` on `RefusedProcessIds.Count == 0`:

```csharp
result.DiscoveryComplete = result.RefusedProcessIds.Count == 0;
```

The root and every openable child are still terminated (`RootExited` stays true), but the receipt now reports partial rather than verified containment, surfacing as `ResponseExecutionStatus.PartiallyCompleted`. The updated test `UnopenableDescendantDoesNotPreventRootKillButTreeRemainsIncomplete` asserts `Success == false`, `DiscoveryComplete == false`, `RootExited == true`, and the refused PID recorded. This removes a fail-open overclaim — containment authority is unchanged, only the honesty of the receipt improved.

### Registry-hint coalescing and alert-text edits

`UnifiedEtwSession` now runs kernel-registry events through `RegistryHintAdmission.Admit` before enqueuing, coalescing repeated per-PID hints within a one-second window (bounded 4096-PID table, cleared on overflow) and incrementing the existing coalesced counter. Registry payloads here are only per-PID WMI hint invalidations, no file-read or process/image evidence is coalesced, and loss/overflow accounting is untouched — so this is queue-flood protection, not a detection drop. The regression test checks that a flood on one PID coalesces while other PIDs and later-window hints still admit, including clock-regression recovery.

The `DnsQueryMonitor` and `PersistentConnectionMonitor` edits only rewrite `Reasoning`/`Evidence` strings and a dedup key (dropping `RemoteIp` from the failover dedup key to reduce duplicate alerts); confidence, tier, and the fire condition are unchanged. These are wording/dedup changes, not threshold changes.

### Certificate response path (unchanged this release)

`AdvancedResponseEngine.cs`, `AdvancedResponseEngine.NetworkActions.cs`, and `CertSuspicionAnalyzer.cs` are unchanged in `d10d1bb..54dbaff` (they differ only in the broader 3.3.9 baseline). The 3.4.6 test delta only adds assertions that the existing `CertificateNotExplicitlyDistrusted` demotion stamps `Tier2`/`LogOnly` — documenting behavior that predates this release, not a new demotion. Called out because it was flagged for scrutiny; no cert response authority was changed here.
